# ADR-028: SARIF Import and Export; CWE on Every Finding

**Status:** Accepted (engineer, 2026-11-22; the export route is `GET /api/projects/{id}/sarif`, the import takes `workspace_id`)  **Date:** 2026-11-22  **Backlog:** B-045  **Builds on:** [ADR-019](ADR-019-finding-identity-and-locks.md) (finding identity and lifecycle), [ADR-016](ADR-016-root-cause-taxonomy.md)

## Context
Buyers already run scanners (Semgrep, CodeQL, dependency scanners) and will not trust a new detector on day one. The product's position is the risk layer above them: take their findings, score them with S/O/D and the catastrophic floor, merge duplicates with ours, and register them in the same lifecycle. SARIF 2.1.0 is the common output format. Security teams and auditors also expect a standard weakness identifier (CWE) on every finding, and a SARIF export so that results flow into GitHub code scanning and other tools.

Today a finding is a `FailureMode` (name, attack chain, business impact, blast radius, trigger, evidence) with identity derived from the code quote in its evidence (ADR-019). It has no source and no CWE.

## Decision
1. **Imported results become findings in the same model.** A SARIF `result` is converted to a `FailureMode` with two new fields on every finding: `source` (`fmea`, or `import:<tool name>`) and `cwe` (`CWE-<number>`, or `unmapped`). Name from the rule's short description or the result message; evidence as `path:line` plus the quoted source lines read from the stored snapshot (so identity works as for ours); attack chain from `codeFlows` steps when present, otherwise one step from the message; trigger and impact filled from the message and rule help where given, else left as "Not specified" (the existing convention).
2. **Import stores, the next scan scores.** `POST /api/import/sarif` (role `scan`) validates and parses the file, converts the results and stores them as *pending imports* for the project. The next scan of that project adds them to the findings it produces and runs them through the same stages as our own (controls, actuary with the severity-aware floor, root cause, validator, remediation), so they receive S/O/D, priority and the catastrophic floor identically. The import response says how many results were read, converted, merged with existing findings, skipped, and why. *Why not score at import:* a second scoring path would duplicate the pipeline; the cost is that imported findings appear scored only after the next scan. A "scan now" button covers the wait.
3. **Merging with ours.** In order: same finding identity (same code quote); otherwise same file, overlapping lines (within 3) and a CWE that does not conflict: the imported finding must have one, and ours is either the same or still unmapped (our CWE is assigned after the merge, by the root-cause stage). A merged finding keeps our text and scores, and records the other tool in `also_reported_by`. An imported finding with no quote and no match is kept as its own finding.
4. **Verification stance.** Imported findings are shown with their source and are **not independently verified by us** until the exploit verifier exists (B-028 phase B). The existing validator challenges them like ours. The interface says so.
5. **CWE.** Taken from the SARIF (rule `tags` such as `external/cwe/cwe-89`, `properties.cwe`, taxa references) and normalised to `CWE-<n>` without zero padding. For our own findings the root-cause analyst call (ADR-016) also returns a CWE; anything that does not match `CWE-<number>` is stored as `unmapped`. No CWE database is bundled, so only ids are shown (names are a later addition).
6. **Export.** `GET /api/projects/{id}/sarif` (role `read`) writes the project's latest scan as SARIF 2.1.0: one run, tool `FMEA Automation`, one rule per CWE (or per finding when unmapped), one result per finding with level from priority (Critical and High `error`, Medium `warning`, Low `note`), the location from the evidence, `partialFingerprints` from the finding identity, and RPN, S/O/D, priority, root cause, lifecycle state and source in `properties`. Imported findings are exported too, with their original tool recorded.
7. **Safety limits.** SARIF files are untrusted input: at most 10 MB and 5,000 results (the rest are counted and reported), parsed with the standard JSON parser only, artifact URIs are never fetched, paths are normalised and made relative (absolute paths, `..` and URL schemes are dropped), and all text from the file reaches prompts only as marked data (`core/untrusted.py`).
8. **Testing.** Import fixtures for Semgrep, CodeQL and one dependency scanner, **written by hand from the tools' documented output shapes** (the tools were not run); the export is validated against the official SARIF 2.1.0 JSON Schema, vendored in the test fixtures with the `jsonschema` package as a development dependency.

## Alternatives considered
- **Score imported findings at import time** (a score-only run on the stored code): immediate results, but a second path through the pipeline and writes into stored scans; rejected for now, revisit if the wait matters to pilots.
- **Keep imports separate from our findings** (a second list): simplest, but defeats the merge, the single risk ranking and the lifecycle.
- **A SARIF library** (e.g. `sarif-om`): typed objects, but an extra dependency for a format we only read narrowly and write simply.
- **Bundle the MITRE CWE catalogue** for names and validation: a larger dependency and update burden; ids are enough for the first release.

## Consequences
- Every stored result gains `source` and `cwe`; results stored earlier show `fmea` and `unmapped` without migration.
- One extra output field in the root-cause call (no extra call). CWE assigned by the model is a suggestion and can be wrong; the unmapped fallback is explicit.
- Hand-written fixtures prove the parser against the documented shapes, not against every real tool version; real exports from the three tools should be added when available.
- SCA (dependency) results are imported but carry package-level locations; they merge only by file and CWE, so many will stand alone.
- The `scan` role can add findings that influence rankings; imports are recorded in the audit log.

## As built (2026-11-22, B-045)
- **Imports stay active.** Every scan of the project carries all its active imported findings, not only new ones, so a finding a tool still reports stays expected and is never called a fix candidate by a scan that did not re-inject it. A newer file from the same tool is that tool's current report: results no longer in it are superseded, so the next scan can mark them fix candidates; results that come back are reactivated. A result is "used" once a scan was saved; a scan that could not be saved leaves imports pending.
- **Two-step merge.** Same code quote merges before scoring (decision 3). Location matches are made after the root-cause stage, which now runs before the actuary: an imported finding with a known CWE is dropped when one of ours has the same CWE in the same file within three lines (the nearest wins and credits the tool). An imported finding without a CWE never merges by location; our own CWE is unknown before that stage, so a location match against it would be a guess.
- **Hostile input.** Every field is type-checked, text is sanitised (hidden characters, HTML comments and tags removed) and bounded, rule CWEs are computed once per rule, the body is read in pieces against the 10 MB limit, nesting too deep is refused. **Residual risk:** sanitising cannot stop plain-text instructions in a rule description; imported text reaches the controls, actuary, validator and linkage prompts as finding fields, not as marked data blocks (only the root-cause analyst wraps it). Imported findings are shown with their source and an administrator controls who may import, but a hostile SARIF file could still try to steer scores.
- **Names.** An imported finding that clashes with another finding in the same scan gets a unique suffix; names equal to registered ones are kept so the same finding stays the same finding across scans.
- Paths keep leading dots; a path that fits more than one stored file is not guessed.
- Not done: CWE names; scoring at import time; real tool exports as fixtures; two simultaneous scans of one project can both read the same pending imports.
